LogIngestLLM

HIGH Featured: strong Security operations, local AI Python, Qwen3-4B (QLoRA), llama.cpp, Sigma

Summary

LogIngestLLM is a local-only log analyzer and analyst co-pilot that runs on a model you fine-tune yourself. It reads Windows Event Logs (including exported .evtx, on any OS), Windows Prefetch, Linux journald and syslog, web server logs and application logs, and picks out the handful of events worth attention. It explains them for people learning to read logs, and gives SOC analysts ATT&CK mapping, indicators, tool detection, a timeline and a cited incident report. Every claim links back to the exact line in the original log, and nothing leaves the machine.

Problem

Logs are mostly noise, and the interesting lines are written for the people who wrote the software. The logs you most need help with are the ones you cannot paste into a cloud chatbot. A small local model can help, but it is fluent and fallible, so the design has to assume it will sometimes be wrong and make that visible.

What I built

  • Triage. Clusters thousands of lines into patterns, scores them (about 65 built-in rules, Sigma rules, severity, bursts, first time on this host, tool signatures) and has the model review the top ones: importance, why it matters, what to do.
  • Whole-log summary and Explain this event. Annotated lines, what normal looks like, and a check-it-yourself command in the native journalctl, grep or Get-WinEvent form.
  • Tool detection. Attacker tools, abused built-ins (certutil downloads, encoded PowerShell, LSASS dumps), scanners and tunnels, with where each one ran from on disk and a flag for user-writable or temp folders.
  • Jump to the event. Every event remembers its file and line, journal cursor or Windows record ID, so it opens in the original log with the surrounding lines.
  • ATT&CK, indicators, timeline and report. Evidence-only technique mapping, one timeline across every log in a scan, and a Markdown or printable report with citations resolved to file:line.
  • Your own model. A keyboard-driven label queue, a QLoRA fine-tune of Qwen3-4B that trains on one 8 GB GPU (about 45 minutes on an RTX 4060 Laptop, 5.8 GB VRAM), a promotion gate, and GGUF export for the bundled llama.cpp engine.
  • Sigma support for Windows (Security, Sysmon, PowerShell) and Linux logs. Rules using aggregations or base64 modifiers are skipped and counted, never half-applied.

How it works

Logs are parsed with their position kept, clustered into patterns, scored by rules, Sigma, tool signatures and novelty, then the top patterns go to the model for triage. A digest drives the cited summary. The analyzer itself is pure Python standard library; the model runs in a bundled llama.cpp engine started on 127.0.0.1.

  • Evidence over eloquence. Model answers cite numbered log lines ([E3]) that open the original file at that line. Tools the model names are dropped unless their evidence string actually occurs in the log.
  • Log text is untrusted input. Prompts say so, model output is parsed as data, and model-named tools and citations are verified against the log.
  • A gate on every change. A known-answer evaluation covers rules, prompts and the model. A new adapter replaces the current model only if it scores better.
  • Local only. No cloud calls and no telemetry. The dashboard binds to 127.0.0.1, checks the Host header, and refuses file browsing if it is ever bound wider. The browser never sends file paths to read.

Evidence

Triage was measured on the same 119 held-out log patterns each time (exact importance level; flags means worth knowing versus noise):

ModelExact levelWithin one levelFlag precisionFlag recall
Qwen3-4B base, no fine-tune34.5%72.3%74.8%100%
v1: rule labels plus Pi and Linux synthetic data67.2%85.7%98.7%85.4%
v2: rebalanced Linux, Windows and web data, tool-aware labels91.6%98.3%100%100%

End to end through the built-in engine (Q4_K_M plus LoRA in llama.cpp, deterministic), the known-answer evaluation passes 95 of 96 checks across five investigations: a Windows intrusion, a Linux break-in, a scanned web server, a failing device and a healthy laptop. The one miss is a training-data gap (privileged-group changes) that is already added for the next retrain. Anyone can reproduce it with python -m logagent eval --model.

What I'd do next

  • Retrain on the miss. The privileged-group-change examples are already added, so the next retrain should close the one failed known-answer check.
  • Code-signed builds. The Windows, macOS and Linux downloads are not code-signed yet, so SmartScreen and Gatekeeper ask once.
  • Remote collection. Collection is local by design. Logs from other machines are analyzed by copying or exporting them here, and I would keep that boundary rather than add a network path for log data.
  • Sigma coverage. Aggregation-based and base64-modifier Sigma rules are skipped today.
